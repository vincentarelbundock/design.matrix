# Remote auto-compression: analysis (design.matrix#8jp3)

Data: `results/results-medium.csv` (run.R, 331 of 366 cells) and
`results/queries-1e+06.csv` + `results/explain/*.txt` (explain.R, n = 1e6,
"discrete" design f1(5) + f2(4) + xd1 + xd2, 980 patterns, ratio ~1e-3).
Every table below is regenerated by `Rscript bench/compression/summarize.R`.
No new benchmarks were run for this write-up.

**Caveat, up front.** The grid ran on a loaded 32-thread machine (other
workers benchmarking). run.R recorded the 1-minute load average per cell:
median 2.4 at n = 1e5, 3.7 at 1e6, **8.7 at 5e6 (max 17.3)**. Absolute times,
and anything at 5e6, are noisy. The ratios compressed/uncompressed within a
cell (both modes interleaved in one `bench::mark()`) are more trustworthy.
FE fits are a built-in noise control: they are never compressed, so both
modes run the same code; their "speedups" range 0.93-1.1. **Treat
differences within about ±10% as noise.** glm speedups are lower at 5e6
(about 2.0-2.3 against about 3); the speedup correlates with load (r = -0.53),
but load and n move together, so the two can't be separated.

## 1. The decision rule as implemented

`R/remote_compress.R`, `dm_compress_cap()` / `dm_compress_worth_ask()`; option
`design.matrix.remote_compress` = `"auto"` (default) | `TRUE` | `FALSE`.
Used by crossprod / X'y (`dm_remote_moments()`), colSums/colMeans
(`dm_remote_colsums()`), and lm/glm (`dmp_patterns()` -> `dm_sql_patterns()`).
FE fits are never compressed (`compress = TRUE` is an error).

1. Only `na.omit` designs with n >= 2. The keys are the input columns of the
   design (`dm_compress_keys()`), plus the colSums group or the glm offset.
2. If any key is DOUBLE: `approx_count_distinct()` per DOUBLE key on a sample
   (`TABLESAMPLE 0.1% (system)` if n > 1e6, otherwise 10,000 rows). If any
   key has more than 0.5 x the sampled rows distinct, don't compress.
3. `SELECT COUNT(*), approx_count_distinct(hash(keys))` over **all rows**
   (one full scan). Compress if est <= `remote_compress_ratio` (0.1) x rows
   **and** est <= `remote_compress_max` (1e6).
4. The compressed scan has `LIMIT cap + 1`, cap = min(n/2, 1e6) under auto.
   If it returns more cells than that, the code gives up and runs the
   uncompressed scan (two scans). The decision is cached per design and
   key set (`D$cache$worth`).

Cost of the decision queries: median 0.008-0.010 s at 1e5, 0.016-0.020 s at
1e6, 0.021-0.030 s at 5e6. This is **about the cost of a whole product**:
crossprod at 5e6 takes 0.024 s uncompressed (discrete). For fits it is
negligible.

The realized ratio is close to the target (factor design at "0.1" is 0.118,
so auto declines there). Absolute times, discrete, n = 5e6 (compressed /
uncompressed, s): crossprod 0.024/0.024 at r = 1e-3 but 0.32/0.024 at 0.1;
glm 0.84/1.71 at 1e-3 and 1.55/1.73 at 0.1; at the same n, factor glm
1.06/2.44.

- **Products.** Factor-only designs: compression gives a small gain (1.2-1.3x,
  near the noise floor) up to 1e-2. Designs with a few discrete numerics:
  break-even at <= 1e-3, then large losses. Compression clearly wins only
  for **wide** numeric designs (15 numeric columns): 2.7-10x up to 1e-2.
  **Grouped colSums loses almost everywhere at n >= 1e6** (up to 50x).
  Uncompressed time is flat in the ratio (0.022-0.027 s at 5e6, discrete).
  Compressed time grows with the number of patterns.
- **Fits.** glm gains 2-4x up to 1e-2 in every design, still 1.1-3x at 0.1,
  and breaks even or loses at 0.5. Unweighted lm gains a modest 1.2x (2-9x
  wide) up to 1e-3, and loses at 1e-2 for discrete at 5e6. **Weighted lm
  mostly loses at n >= 1e6** unless wide.
- **What auto actually does.** It compresses every design up to 1e-2
  (discrete up to 0.1 for n <= 1e6). So it compresses in exactly the cells
  where products lose: discrete crossprod at 5e6, 1e-2, is 4.7x the better
  mode; colSums(g) at 5e6, 1e-3/1e-2, is 6-19x. Auto time (decision + chosen
  mode) / better mode, median (max): crossprod 1.83 (5.4), colSums(g) 1.77
  (19), lm 1.17 (2.4), weighted lm 1.15 (3.6), glm 1.04 (3.1). The decision
  is cached, so repeated products on one design pay it once.
- **Keys and threads** (side grids at 1e6 and 5e6, r = 1e-3 and 0.1). ENUM
  keys speed up both modes by 25-45% (uncompressed a bit more). One thread
  slows everything 2.2-3.3x, except uncompressed colSums(g), which slows
  4.7x against 1.8x compressed; even so, compression still loses (0.44).
  Only 4 of 96 cells change winner by more than 20%, so the conclusions are
  unchanged.
- **Memory.** `mem_alloc` counts R allocations only: the dense cell design
  (G x p) and the IRLS state on it. It grows with patterns. Median at
  n >= 1e6, r = 0.1: crossprod 211 MB compressed vs 0.6 MB uncompressed; glm
  1.4 GB vs 6 MB; at r = 0.5, glm 4.6 GB. Peak RSS (R + in-process DuckDB,
  above baseline; a lower bound, noisy, occasionally negative) shows the same
  pattern. Maximum over the grid: colSums(g) 3.7 GB compressed vs 44 MB;
  crossprod 3.7 GB vs 1.0 GB; glm 0.85 vs 0.77 GB. Auto's 0.1 / 1e6 caps
  bound this.

## 3. Mechanism (EXPLAIN ANALYZE and query profile, n = 1e6)

**Products are one scan in either mode.** Both are a single
`WITH b AS (...) SELECT ... GROUP BY ALL`. The uncompressed scan is
*already* an aggregation: it groups by the factor cells and sums the products
of numeric columns per cell. The compressed scan instead adds the numeric
columns to the key and sums only counts and weights:

- crossprod uncompressed: `GROUP BY` over `__dm_c1, __dm_c2` with
  `SUM(__dm_v3 * __dm_v3)`, ... → `Hash Group By 20 rows 10.0ms`, Total Time
  0.0082 s.
- crossprod compressed: `GROUP BY ALL LIMIT 1000001` with keys
  `__dm_v3, __dm_v4, __dm_c1, __dm_c2` → `Hash Group By 980 rows 20.0ms`,
  Total Time 0.0091 s. Table Scan is 20 ms in both.

So compression trades per-row arithmetic (about m(m+1)/2 numeric products,
m = numeric columns) for a larger hash table (G entries instead of the factor
cells), plus moving G rows to R and building a dense G x p design there
(`dm_sql_cell_design()`). With m = 2 there is nothing to save, and G only
hurts. With m = 15 (wide) the uncompressed plan spends `Projection 1,000,000
rows 70.0ms` computing 120 products, plus `Hash Group By ... 70.0ms` (total
0.045 s). The compressed plan takes 0.021 s. Grouped colSums is worse still:
uncompressed groups by g x factor cells (`Hash Group By 200 rows`), while
compressed groups by g x patterns (`9,800 rows 40.0ms`). And colSums has no
products to save. Factor-only designs are near 1x because there, both modes
group by the same joint factor cells.

**Fits re-scan the rows; compression replaces the scans with one GROUP BY.**
Per-statement profile (seconds of SQL):

| op | mode | statements | SQL s | total s |
|---|---|---|---|---|
| glm (4 iter) | uncompressed | 28 | 0.838 | 1.008 |
| glm (4 iter) | compressed | 16 | 0.229 | 0.279 |
| lm | unc / comp | 12 / 9 | 0.054 / 0.043 | 0.075 / 0.056 |
| weighted lm | unc / comp | 13 / 11 | 0.066 / 0.082 | 0.089 / 0.097 |
| crossprod (wide) | unc / comp | 1 / 1 | 0.052 / 0.024 | 0.098 / 0.026 |

- Uncompressed glm runs three row statements per IRLS iteration: deviance
  sums, validity sums, and a moments scan (0.192 s per iteration). The moments
  scan joins eta from the coefficient table (`Hash Join ... Conditions:
  __dm_c1 = k1`) and evaluates the inverse link inline. The statement
  contains `exp(` 17 times per row. Its plan takes 0.055-0.066 s (Total Time),
  against 0.008 s for a linear moments scan over the same rows.
- Compressed glm runs **one** pattern scan (0.014 s; `Hash Group By 980 rows
  30.0ms`), then iterates in R on 980 rows. What's left is fixed row work: the
  starting deviance (0.025 s) and the final summaries on the rows (a moments
  scan of 0.028 s and sums of 0.086 s). That fixed work is about 0.18 s of the
  0.23 s of SQL.
- Unweighted lm makes a single pass either way. The gain (1.2x) is fewer
  auxiliary statements, with `var_pop(y) * COUNT(*)` giving the within-cell SS
  in the same scan. Weighted lm needs a **second pass**, the "within pass":
  `b JOIN p ON` the cell means, 0.028 s. That makes compression a net loss.

## 4. Durability

- **glm: structural.** IRLS needs one pass over the data per iteration, with
  a nonlinear link evaluated per row. Compression needs one pass in total.
  Suppose each uncompressed iteration were fused into a single scan: from the
  profile, about 0.11 s per iteration (the moments scan alone) instead of
  0.19 s. Then uncompressed ≈ 0.18 + 4 x 0.11 ≈ 0.62 s against 0.28 s
  compressed: still about 2x. The gain shrinks only with fewer iterations or
  more patterns, and the second follows from the ratio.
- **Products: also structural, in the other direction.** The uncompressed
  scan is already a GROUP BY over factor cells. Compression can only add keys
  (numeric values), so it can only make the hash table bigger. It pays only
  when it removes enough per-row arithmetic (many numeric columns, few
  patterns). This follows from the SQL shapes, not from the current DuckDB
  version. The exact breakpoints (where wide stops winning) are
  engine-dependent.
- **Weighted lm: not structural.** The loss comes from the two-pass weighted
  within-cell SS, which is an implementation choice.
- **Decision cost: structural for products.** A full-scan
  `approx_count_distinct` costs about the same as the product itself.

## 5. Options and recommendation

| option | effect | code it simplifies |
|---|---|---|
| A. keep as is | products lose up to 5x (crossprod) and 19x (colSums(g)) in auto cells; 1.8x median from the decision alone | none |
| B. drop compression for products | lose 2.7-10x on wide designs; no decision cost on products | cap branches of `dm_sql_moments()` (about 10 lines) and `dm_sql_colsums()` (about 15) in `R/remote_sql.R`; `dm_remote_moments()` / `dm_remote_colsums()` in `R/remote.R` (about 5); about 20 test lines in `inst/tinytest/test_remote_compress.R`. `R/remote_compress.R` (181 lines), `dm_sql_scan()`'s `by` and `limit`, and the decision all stay for fits |
| C. retune per operation (recommended) | auto: colSums/colMeans never; crossprod/X'y only for many numeric columns (wide) with ratio <= 1e-2, skipping the decision otherwise; glm as now (could allow up to about 0.2); lm ratio <= 1e-3; weighted lm only for wide, or fix the second pass | adds a little: a per-operation ratio or a numeric-column test in `dm_compress_cap()` |

**Recommendation: C, not removal.** Option B would remove only about 30-35
lines out of about 10.6k. Fits still need the whole compression machinery
(`dm_sql_patterns()`, `dm_sql_cell_design()`, `dm_compress_worth()`), so B
doesn't "considerably simplify the code", and it gives up real wins on wide
designs. The reasons are understood and durable, as section 4 explains. But
the payoff from removal is small, while a retune captures nearly all the
gain. The simplest version of C: products never compress under auto unless
the design has many numeric columns (and colSums never), with `TRUE` still
forcing it. This also removes the decision cost from most products. As a
separate item, the weighted within-cell SS could become one pass, or a
row-level RSS after the fit, as uncompressed does. Any of this is a separate
step that needs Vincent's approval. This analysis changes no code.

**Uncertain.**

- **35 cells are missing.** All 30 wide cells at n = 5e6 (r = 1e-4 ... 0.5,
  every op). The factor cells at 5e6, r = 0.5 for colSums(g), lm, weighted
  lm, glm and FE (5); crossprod ran there. The wide 5e6 cells are where the
  product wins live, and those wins shrink from 1e5 to 1e6 (crossprod 9.9 to
  4.3 at 1e-4). So it is open whether wide products still win clearly at 5e6.
  The numeric-column threshold for C sits somewhere between 2 (loses) and 15
  (wins), and isn't measured. n = 5e7 was never run.
- **Load noise.** 5e6 cells ran at load 3-17. Conclusions resting on 1.1-1.3x
  are within noise: factor crossprod, unweighted lm, glm at 0.1 (discrete).
- **Coverage.** One link (logit), one weight pattern (w in 1:3), ungrouped
  colSums not timed, a single machine, and DuckDB only.
